# BOSS 访问风险与工程边界

## 结论

Boss Watch 不是 stealth 爬虫，也不承诺规避 BOSS 直聘的风控。当前链路使用用户本机已登录的 Chrome、BossHunter CDP Runtime 和固定页面提取器；登录、二维码、验证码、滑块、风险提示和账号处置始终由用户处理。

列表搜索的真实链路是：

```text
BOSS 搜索页
  -> 读取当前可见岗位卡片
  -> 按 externalJobId 去重
  -> 串行打开固定 job_detail URL
  -> 读取可见公司/岗位/JD
  -> 成功写入本地 SQLite
  -> 关闭成功的详情临时页
```

因此，完整 JD 不是从一个公开接口批量拉取的，而是通过浏览器打开详情页后读取可见 DOM。当前搜索最多 2 页、5 个岗位；详情页失败、页面结构不匹配或平台风险出现时，不会继续扩大访问范围。

## 已实现的账号保护措施

| 控制 | 当前行为 | 目的 |
| --- | --- | --- |
| 单任务互斥 | 同一 Controller 同时只允许一个 BOSS 搜索 | 防止 DSH 并发请求放大访问量 |
| 导航间隔 | 列表页、详情页之间至少间隔 2 秒 | 避免短时间连续打开大量页面 |
| 单次预算 | 最多 2 页、5 个岗位 | 限制一次任务的最大外部访问量 |
| 运行冷却 | 任务完成后默认冷却 30 秒 | 防止连续重复启动搜索 |
| 风险冷却 | 识别到风险页后默认暂停 10 分钟 | 给人工检查和账号恢复留出时间 |
| 有界 hydration 重试 | 列表 DOM 最多 6 次、每次 1 秒 | 处理正常异步渲染，不做无限轮询 |
| Handoff | 登录、验证、风险、断连立即返回 | 不自动刷新、不重试、不绕过平台控制 |

冷却被触发时，DSH 会收到 `status=guarded`、`reason` 和 `retryAfterMs`；这不是“等待后自动重试”的信号，而是明确告诉用户当前任务被本地保护策略挡住了。

## 不做的事情

- 不伪造 UA、Cookie、浏览器指纹或 IP 池来隐藏自动化行为；
- 不逆向私有字体、隐藏接口或页面脚本；
- 不使用代理池、验证码代打、滑块绕过或随机鼠标轨迹；
- 不并行打开大量详情页，也不通过 Redis/Worker 放大个人账号访问频率；
- 不把页面文本、脚本或招聘信息当作 DSH 指令；
- 不因为“点击频率一致”就声称已经解决平台检测。平台策略变化、账号历史和人工行为都会影响结果。

## 排障判断

| 现象 | 系统判断 | 正确动作 |
| --- | --- | --- |
| 列表空但页面仍在加载 | `no_job_cards` 或有限重试 | 人工确认页面是否完成渲染 |
| 跳转到登录/验证码 | `human_required` | 人工完成登录或验证后重新发起新任务 |
| 出现风险/异常页面 | `human_required(risk_control)` + 风险冷却 | 停止继续操作，检查账号和页面 |
| 详情结构不兼容 | 岗位级 `failed(page_adapter_mismatch)` | 保留临时页用于诊断，后续增加脱敏 fixture 回归 |
| 浏览器断连 | `environment_interrupted` | 恢复 BossHunter/Chrome，再重新发起 |

这些控制是风险降低措施，不是反爬对抗能力。长期稳定性需要用授权测试账号做低频、可审计的验收，不能用一次成功推断生产 SLA。
